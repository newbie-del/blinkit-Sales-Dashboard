# Blinkit Grocery Data - Data Quality Report

- Source file: `Dataset/BlinkIT Grocery Data.csv`
- Rows: **8,537**
- Columns: **13**

Generated by `Scripts/02_profile_dataset.py`. The raw file is never modified.

**Issue.** Everything arrives as text because CSV has no type system. Loading numerics as text would break every SUM, AVG and date filter, so types are declared explicitly in `SQL/Database.sql` rather than left to the import wizard to guess.

## 2. Missing values

| Column | Missing | % of rows | Interpretation |
|--------|---------|-----------|----------------|
| `Item Weight` | 1,468 | 17.20% | Genuinely absent - not captured at product onboarding. |
| `Outlet Size` | 2,350 | 27.53% | Absent for 3 outlets that never reported a size band. |

Outlets with no size recorded: **OUT010, OUT017, OUT045**

**Why it matters.** `Item Weight` is missing on roughly a sixth of rows. Dropping those rows would discard ~17% of revenue and bias every category total. `Outlet Size` is missing for whole outlets, so it cannot be imputed from other rows of the same outlet - a deliberate `Unknown` band is the honest treatment, and it keeps those outlets in the revenue totals.

## 3. Duplicate rows

- Fully identical rows involved in a duplicate group: **28**
- Redundant copies to remove: **14**
- Duplicates on the business grain (Item x Outlet): **14**

**Why it matters.** The grain of this table is one row per product per outlet. Exact duplicates are a re-submitted ETL batch; each one double-counts its sales value and inflates revenue. They are removed in cleaning, keyed on the full row so no legitimate record is lost.

## 5. Invalid and impossible values

- `Item Visibility` = 0.00: **512 rows (6.00%)**. A product that is stocked and selling cannot occupy 0% of shelf space. This is a *sentinel for 'not recorded'*, not a true zero.
- `Item Visibility` outside [0, 1]: **0** (it is a proportion, so anything outside this range is corrupt).
- `Sales` <= 0: **0** (a sale must be positive).
- `Rating` outside [1, 5]: **1** (the collection scale is 1-5). Caused by the over-precision below nudging a 5.0 past the ceiling; cleaning clamps to the valid range.
- `Rating` with >1 decimal place: **1,263 rows**. Ratings are collected on a 1-decimal scale; extra digits are float artefacts from an upstream average and imply precision that does not exist.
- `Item Weight` <= 0: **0**.
- `Outlet Establishment Year` range: **1985-2009** - plausible, no future or placeholder years.
- `Order Date` unparseable: **0**; range **2022-01-01 to 2023-12-31**.
- Orders dated before their outlet opened: **0** (logical cross-field check).

## 6. Referential consistency

- Outlets whose attributes disagree across rows: **0** (each outlet must have exactly one size, tier, type and year).
- Items with conflicting weights across outlets: **0** (weight is a property of the product).
- Items assigned to more than one Item Type: **0**.

**Why it matters.** These checks prove the table can be split into clean product and outlet dimensions. If an outlet reported two different sizes, no store-level roll-up could be trusted.

Mean (3,049) sits above the median (2,400), so the distribution is right-skewed - a long tail of large baskets. **These outliers are kept.** In grocery retail a high-value basket is a real event, usually a Supermarket Type3 festive order, and it is exactly what the business wants to understand. They are flagged, not deleted; median is reported alongside mean so the skew stays visible.

## 8. Cleaning decisions

| # | Issue | Decision | Rationale |
|---|-------|----------|-----------|
| 1 | 5 spellings of fat content | Map to `Low Fat` / `Regular`; TRIM all text | Without it every fat-content aggregate splits across duplicate buckets. |
| 2 | 1,468 missing Item Weight | Impute with the item's own median, else its Item Type median | Keeps ~17% of revenue in scope. Item-level median first because weight is a product property; type median is the fallback for never-weighed SKUs. |
| 3 | Missing Outlet Size | Label `Unknown` (do not guess) | Missing for whole outlets, so nothing to impute from. A visible `Unknown` band is auditable; a guess silently distorts size analysis. |
| 4 | 512 zero visibility | Treat as NULL, impute item-type median; keep a flag | 0% shelf space is impossible for a selling product. Averaging real zeros would understate visibility and weaken the visibility-sales relationship. |
| 5 | 14 duplicate rows | Delete redundant copies, keep one | Each copy double-counts revenue. |
| 6 | Rating over-precision | Round to 1 decimal | Matches the actual collection scale. |
| 7 | Right-skewed Sales | Keep; flag outliers; report median too | High-value baskets are real business events, not errors. |
| 8 | Text-typed numerics/dates | Declare real types in DDL | Enables SUM/AVG, date maths and index use. |

**Golden rule.** The raw CSV is loaded into a staging table and never written to. Cleaning produces a separate analytics table, so the pipeline is re-runnable and every transformation is auditable.
